# 故障定义与证据规范（统一定义）

> 本文档统一「现存研判」与「预测预警」对"故障"的定义、证据要求与严重程度分档。
> 代码实现必须以此为准；出现分歧时先改本文档，再改代码。
>
> 版本：v1（2026-01 制定）｜适用范围：接口 2 `/api/analyze/anomaly`、接口 11 `/api/forecast/preview`

## 1. 为什么要统一定义

两套逻辑原先各自演进，实测在**故障边界窗口**上结论相反：

| 窗口 | 研判结论 | 频谱口径 | 矛盾 |
|---|---|---|---|
| EV-001 AP-02 `01-01 10:00~10:15` | 正常 | 越阈 | 研判漏报 |
| EV-005 AP-02 `01-04 10:00~10:15` | 边缘弱用户 | 未越阈 | 研判误报 |
| EV-006 AP-01 `01-05 20:00~20:20` | 正常 | 越阈 | 研判漏报 |
| EV-007 AP-01 `01-06 10:00~10:15` | 边缘弱用户 | 未越阈 | 研判误报 |

56 个事件边界窗口中有 **4 个（7%）结论相反**。根因是两套判据的**统计对象不同**：

| 维度 | 研判（现状识别） | 预警（未来预测） |
|---|---|---|
| 数据源 | 网络表（每 UE 每分钟采样） | 频谱表（每 AP 每频段每分钟） |
| 统计对象 | 窗口**均值** + 标签**占比** | 每分钟**越阈频段计数** |
| 时间粒度 | 窗口整体（可跨小时切片） | 分钟级连续 |
| "严重"定义 | `weak_ratio > 0.5` | 越阈频段比例 ≥ 0.5 |

**注意：统计对象不同是合理的（两个维度本来就该看不同东西），但"什么算故障"必须是同一套。**

## 2. 统一定义的三个层次

### 2.1 第一层：判定单元

```
判定单元 = (AP, 分钟)
```

- 不再把"窗口均值"同时当作判定对象和判定依据。
- 窗口只是**查询范围**：窗口内的判定结果由逐分钟证据汇总而来。
- 窗口过短时（< 20 行采样 / < 20 分钟）**不单独下"故障"结论**，最多给"提示"。
  （已实现：`MIN_HOUR_ROWS = 20`）

### 2.2 第二层：主判据（任一维度满足即判故障）

| 故障类型 | 主判据 A（频谱维度） | 主判据 B（网络维度） |
|---|---|---|
| **弱覆盖** | 功率 < −95 dBm 的频段 **≥40/50**，且**连续 ≥3 分钟** | RSRP < −105 dBm 的**采样占比 ≥ 30%** |
| **拥塞** | 占用率 > 80% 的频段 **≥40/50**，且**连续 ≥3 分钟** | `congestion` 标签占比 **≥ 25%**，或 PRB 均值 > 90% |

**为什么"任一维度即可"**：两个维度测的是不同物理量（用户级 RSRP vs 频段级功率），
一方越阈就已经构成事实；要求两者同时满足会漏掉 EV-001 / EV-006 那类"频谱先坏、标签后到"的情形。

**为什么阈值是 −95 dBm / 80% / 40 频段 / 3 分钟**：
- −95 dBm 与 80% 均来自 `docs/api.md` 的频谱转交口径
- 40/50 频段 = 80% 频段同时越阈，用于滤掉边缘频段噪声（实测只按 5/50 判定时正常时段也误报）
- 3 分钟连续性用于滤掉单分钟抖动（实测只按单分钟触发时正常时段也出现过误报）

### 2.3 第三层：严重程度分档（两维判定）

| 等级 | 条件 | 语义 |
|---|---|---|
| **严重** | 两个维度**都**满足主判据 | 已确证，影响用户且频段级异常 |
| **中等** | **仅一个**维度满足 | 已发生，另一维度尚未跟上（常见于爬坡期/恢复期） |
| **提示** | 都未达主判据，但**过半采样 SINR < 5 dB** | 性能偏低，**不算故障** |
| **正常** | 以上都不满足 | — |

**"提示"不是故障**：不进入 `affected_aps`、不生成处理方案、不计入异常统计。
（已实现：`judge_ap` 返回 `性能提示`，`findings` 过滤时排除）

## 3. 时间语义（已实现）

窗口是"过去 N 分钟"，窗口内出现过异常 **≠** 此刻仍在故障。接口必须分开表达：

| `current_state` | 含义 | 判定 |
|---|---|---|
| `fault_active` | 当前仍在故障 | 最后一段异常结束时间距窗口末尾 ≤ 10 分钟 |
| `recovered_in_window` | 窗口内发生过、现已恢复 | 有异常区间但末尾已恢复 |
| `performance_warning` | 仅"提示"级 | 无故障但有性能提示 |
| `normal` | 正常 | — |

配套字段：`anomaly_spans`（分钟级起止）、`last_anomaly_at`、`performance_hints`。

## 4. 证据要求（强制）

**任何"故障"级结论都必须携带触发证据**，格式：

```json
{"metric": "rsrp", "avg_value": -111.2, "threshold": -105, "status": "异常"}
```

规则：
1. 结论为"覆盖故障 / 网络拥塞 / 边缘弱用户"时，`kpi_evidence` 不得为空。
2. 证据必须包含**触发该结论的具体指标 + 实测值 + 阈值**，不允许只给文字描述。
3. 由标签占比触发的结论（如 `weak_ratio > 0.3`），证据里必须显式给出该占比
   （metric = `weak_coverage_ratio`），不能只写"弱覆盖采样占比高"。
4. "提示"级结论同样需要证据（`status = "提示"`）。

> 现状：`边缘弱用户` 已补齐证据；`覆盖故障`/`网络拥塞` 目前由 `weak_ratio`/`cong_ratio`
> 触发时证据可能为空 —— **待改**（见第 6 节）。

## 5. 两个用途共用同一套定义

```
统一判据（本文档第 2 节）
   ├── 用于「现状识别」：输入=历史窗口 → 输出 current_state + anomaly_spans + 方案
   └── 用于「未来预测」：输入=历史窗口 → 推未来 → 同一判据作用于预测值 → 输出 alerts
```

**区别只在时间方向**，不在判据。因此：

- 研判说"弱覆盖"、预警说"无风险"是**不允许**的（除非两者时间窗不同，且必须在文案里说明）
- 预警的"预计 N 分钟后越阈"与研判的"已越阈"使用**同一阈值**

## 7. 验收方法

改完后必须能通过以下三项，缺一不可：

| 验收项 | 方法 | 当前基线 |
|---|---|---|
| 命中 / 漏报 | `python scripts/accept_forecast.py` | 8 / 8，漏报 0 |
| 误报率 | 同上（非事件时段抽样） | 0.29%（5 / 1741） |
| **两套口径一致率** | 事件边界窗口（56 个）逐窗口对比 | **52 / 56 = 92.9%** |

第 3 项是本规范的核心指标：改完后一致率应提升，且命中率不得下降。

复跑一致性对比：

```powershell
python scripts/compare_verdicts.py                  # 事件边界窗口（56 个）
python scripts/compare_verdicts.py --all-windows    # 额外包含事件整体窗口
```

退出码：0 = 全部一致；1 = 存在不一致（便于后续接入 CI）。
